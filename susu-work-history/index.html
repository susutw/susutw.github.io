風控 · 2024 年主線

把寫死在程式碼的風控規則，變成營運可自助設定的引擎

反詐規則原本硬編碼，營運每次要調整判斷條件，都得走一次開發、測試、發版—— 詐騙手法變化的速度比發版週期快。我從系統分析做到上線，讓營運能自行新增、編輯、 上下架規則；但沒有因為開放設定而失去控制：規則變更走「草稿 → 送審 → 審核」， 強制申請人與審核人分離，所有異動留可追溯 log。後續為規則與商品清單加上快取處理效能。

訊號

上線前修掉 38 項 QA 缺陷，其中最關鍵的一項是：「申請人與審核人不可為同一人」 這條檢核根本沒有被實作。那不是功能 bug，是整套雙人覆核形同虛設—— 功能能跑，不代表控制有效。

架構 · 2024 — 2025

把單一事業體的風控系統，改造成同時服務三個事業體

在不重寫系統的前提下，導入 merchant 維度貫穿所有風險分析 API、規則管理 API、 資料表與後台操作介面，並完成既有資料回填——回填是整個遷移最容易出事的一步。 各事業體的規則、審查單與報表必須互相隔離：不能讓一邊的黑名單影響另一邊的訂單。

訊號

過程中抓出並修掉三個租戶邊界洩漏，最棘手的一類是累計型規則的計數範圍沒跟著事業體切開—— 規則本身寫得對，但累積狀態是共用的，於是一邊的行為會影響另一邊的判定結果。 隔離不只要做在查詢條件與資料表上，也要做在狀態累積的邊界上； 後者不會在功能測試中出現，只有拿兩個租戶的資料交叉跑才看得到。

金流 · 2026

跨 7 個服務交付一種支付方式，並為既有商家寫可重跑的批次遷移

新商家開通不難，難的是既有已綁定金流商的商家要批次補開，而兩邊系統的狀態可能不一致。 幾個刻意的風險控制決策：閘道介接版本升級只對這一種支付方式生效，不動其他支付； 推送 payload 改以金流商端現有設定為權威來源，避免覆蓋商家在那邊已有的設定； 批次腳本設計為冪等可重跑；並修掉一個狀態機錯誤——金流商拒絕申請時，原本會誤觸發「開通成功」的 callback。

訊號

交付的不只是功能，是一份寫明驗證盲區的上線 SOP：dry-run 驗不到寫入路徑， 也驗不到有沒有真的打到金流商，所以一定要先做單店金絲雀；而且我們系統標記「已開通」 不等於金流商真的開通了——還需要對方送審與網域註冊。系統做完，不等於事情做完。

支付風控

動態 3DS

全部交易都要 3D 驗證會殺掉轉換率，全關則擋不住盜刷。設計依交易與商品風險等級 動態決定是否要求驗證的機制，並持續調校三年，同步解決風控與支付兩系統間的商品清單一致性問題。

第三方整合

外部反詐服務端到端串接

難點從來不是呼叫 API：負責送單條件設計（控制外部服務用量）、資料契約正確性、 訂單狀態雙向同步、決策整合，並處理上游呼叫次數上限、回應延遲，以及外部失敗不該弄垮自家系統。

合規

會員刪除與去識別化

跨會員、風控、批次三個服務。刪除是不可逆操作，因此加上次數限制與 LOCK 機制防止 重複提交與併發；上線前先驗證與既有「合併帳號」功能的交互影響。

診斷

64 件生產環境問題

包含偶發競態條件、時區基準錯配（第一版沒修乾淨，邊界條件仍漏抓，補第二個修正才收乾淨）， 以及症狀與根因完全不相關的中斷——「無法寄送通知信」的真因是 SDK 在舊版 PHP 下 產生 deprecation notice 導致 502。

主動性

效能、韌性與資料治理

同批優化 4 支關鍵路徑 API、一次補齊 4 支 API 的 DB／Redis 連線異常處理、 六度執行索引治理、建立過期資料清理排程，並主動下架不該保存的卡號與 IP 資料—— 那是沒人要求、但該做的事。

團隊槓桿

把經驗變成別人能用的東西

879 次 code review、248 次發版、17 份團隊維運 runbook。runbook 不只寫「怎麼修」， 而是寫「為什麼會這樣」與「哪裡最容易誤判」；該知識庫同時供團隊成員與 AI 開發工具載入使用。
