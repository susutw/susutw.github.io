四個半月，五層能力

從個人試用到內部工程能力

2026 年 3 月，團隊開了第一張「Claude Code 研究」票。四個半月後，AI 輔助工作不再是個人工具， 而是一套有知識庫、有資料存取層、有權限治理、有託管平台的部門能力。 這頁記錄怎麼蓋的、蓋了什麼、以及還缺什麼。

方向

宣告了三條軸線，資源實際押在一條

2026 年 4 月同一天立了三個 Epic，把 AI 導入切成互不重疊的三條軸線。 四個半月後的落地程度差距很大——這個落差本身是最值得記錄的觀察。

實質落地

對內：開發流程

把 AI Agent 導入 RD 開發流程，提升效率與品質。知識庫、資料存取、 sub-agent、治理規則全部就位，且產出超出原訂範圍。

原範圍中「code review 自動化」與「需求回報時 agent 協助填寫」尚未產出。

地基已備

對客戶：自然語言查詢

讓客戶用自然語言查自己的訂單與報表。託管架構與「員工／外部」雙信任邊界 已設計完成，報表服務已建置，但尚未有外部單位實際上線。

架構的正確性還沒被真實流量驗證過。

僅立項

對產品：功能整合

把 AI 應用整合進產品本身，降低商家的使用門檻與上架成本。 目前仍在規劃階段，未拆解、未指派。

唯一寫了明確效益假設的軸線，也是唯一完全沒動的。

實際產出最多的其實是第四條沒有事先立項的軸線——QA 測試流程的 AI 化， 佔全部 AI 相關工單的三分之二。它的 Epic 是在大量產出開始之後才補立的。
成果

由下而上的五層

層與層之間是真的依賴順序：沒有可信的知識，AI 的答案不能用； 沒有資料存取，知識就只是靜態文件；沒有治理，前面三層不敢放給全隊用。

01

知識庫 — 索引與知識分離

在專案目錄開啟工作階段時，一份索引檔會自動載入。它不含知識本身， 只含「什麼症狀該讀哪份 runbook」的路由表。細節放在 70 份獨立 runbook 裡按需讀取。

runbook70 份 / 13,318 行 / 674 KB
自動載入的索引277 行（僅路由）
最大類別QA 測試流程 15 份
涵蓋範圍金流、通路整合、K8s、資料庫、前後端開發、場域設備、翻譯流程
這個結構是撞牆後才調出來的。知識庫上線第二天，索引檔就因為塞入架構說明膨脹到近 400 行。 隔天一次砍掉 305 行、把內容拆成獨立 runbook。原則是：自動載入區只放路由，不放知識—— 索引成長是線性的，知識量成長才不受限。
02

資料存取層 — 16 個唯讀資料源

透過 MCP（Model Context Protocol）把資料源接進工作階段，讓 AI 能查真實狀態而非只讀文件。 全部唯讀，安裝流程選單化、憑證自動讀取。

關聯式資料庫8 個（主資料庫與金流庫 × 四環境）
文件資料庫3 個
Log 系統2 個
工單與其他3 個
連 production 資料庫不走 VPN，改走雲端 session manager 建立本機通道。 並且把「確保通道存在」寫成工具執行前的自動 hook—— 使用者不必記得先開通道，要用的時候它已經在了。
03

執行單元 — 3 個 sub-agent、4 個 skill、6 個指令

三個唯讀 sub-agent 分別承接工單分流、深度調查與知識查詢。 設計重點不是能力更強，而是 context 隔離：把掃 log、grep 多個專案這類吵雜的中間過程 關在各自的 context，只把結論與精選證據回傳主線。

自動化程度最高的 skill一句話跑完 14 步 API 鏈，在三個測試環境建商品並供貨到通路直到「已串接」——三環境皆實測
測試流程從規格文件自動生成測試案例，並匯入測試管理系統
知識回填從當前對話萃取知識、找落點、自動開分支發 PR
收工儀式掃當日工作、篩出值得寫進知識庫的候選
成本也是架構決策。三個 sub-agent 都在定義檔寫死使用較便宜的模型，不繼承主線。 它們承接的是掃 log、grep、讀文件這類機械工作，品質瓶頸不在模型智能—— 而預設繼承是最貴的選項。這條後來寫成規範：新增 agent 必須一併指定模型。
04

治理 — 29 條禁用、22 條允許，進版控全員共用

權限政策寫成設定檔進版控、全隊生效，個人化部分另放不進版控的本地檔。 禁用規則涵蓋所有環境的資料庫寫入操作，以及推送到主分支。

憑證隔離連線設定、共用 service account、個人工作階段狀態全部排除於版控之外
已驗證311 個 commit 全掃，資料庫密碼命中數 0
貢獻規範明文規定什麼不該進知識庫，PR 檢查清單第一條就是機敏資訊掃描
不同資料源的安全預設不一樣，不能類推。 其中一類資料庫的 MCP server 本身就以唯讀交易執行查詢，天生擋掉寫入； 另一類完全沒有這層保障，因此用 27 條規則逐一擋掉所有寫入工具。 若假設「MCP 都是唯讀的」而不逐一確認，那一類就是敞開的。
05

託管平台 — 雙信任邊界、四層防禦

自架 MCP 服務的完整架構，讓資料存取能規模化，也是對外開放的前提。 核心是把員工自用與外部串接定義成兩條永不共用的信任邊界—— 不共用閘道、不共用防火牆規則、不共用命名空間、不共用資料庫帳號。

四層防禦網路層 IP 白名單 → 身分授權層 SSO 與白名單 → 應用層唯讀護欄 → 資料層最小權限憑證
通用性前三層對任何 MCP 類型完全相同，只有最底層的憑證隨類型而變
白名單分兩層「誰能用」精細到每個資料源、走 GitOps 審核；「從哪裡連」全閘道共用
審計單一紀錄同時記身分、使用的工具與查詢內容
邊界用命名劃死，不只寫在文件段落裡。 兩類的前綴一路貫穿網址、命名空間、路由、後端服務、資料庫帳號與用戶端名稱。 命名一致時，誤配會在 review 時看起來很刺眼；命名不一致時，誤配看起來很正常—— 而誤配的後果是內部資料暴露到公網。

可以直接抄的四件事

如果你的團隊也要導入 AI 輔助工作，這四個岔路一定會遇到。

知識設計

寫「哪裡最容易誤判」，不只寫「怎麼做」

給人看的 SOP 可以只寫步驟，因為人看到不合理的結果會停下來質疑。 AI 不會——它會因為「看起來合理」而繼續往下走，把錯誤結論講得很有信心。

所以知識庫刻意大量記錄反直覺的陷阱：查錯環境時 log 會回空而不是報錯、 某個過濾條件的字面意思與實際行為相反、dry-run 成功驗不到寫入路徑、 自家系統標記「已完成」不等於外部系統真的完成。 價值密度不在正確步驟，而在「錯誤但看起來正確」的路徑。

架構

自動載入區只放路由，不放知識

會自動載入的檔案越大，每次工作階段的固定成本越高，而且大部分內容跟當下任務無關。

拆成「索引 + 按需讀取的 runbook」之後，索引成長是線性的（每份文件一兩行）， 知識量成長不受限。若把知識直接寫進自動載入區，會在幾十份文件後撞牆。

成本

把模型選擇當架構決策，不是憑感覺

不指定時，sub-agent 會沿用主線模型。但它們承接的多是掃 log、grep、讀文件這類機械工作。

三個 sub-agent 全部在定義檔寫死使用較便宜的模型，並寫進規範：新增 agent 必須一併指定。 預設繼承是最貴的選項。

治理

「有寫 .gitignore」不等於「沒洩漏」

憑證隔離的設計要實際驗證，不是宣告了就算。

這次盤點實際掃過全部 311 個 commit 的歷史，確認資料庫密碼命中數為 0、 連線設定檔從未進入版控。掃過才算驗證。 殘留風險也一併記錄：本機的連線設定仍是明文，這是該類 MCP 的固有限制，非設定疏失。

還缺什麼

地基蓋得紮實，但沒有儀表板

盤點出來最該補的一項，不是再多做一個 agent。

目前所有成果都是產出量指標，沒有一個效果指標。 70 份 runbook、16 個資料源、3 個 agent——這些都能數， 但「導入 AI 讓我們快了多少」目前無法回答。向上要資源、決定下一季是否繼續投入， 靠的都是效果數字。
最容易補的量化 工單排查耗時（工單系統有現成資料）、測試案例產出速度、建商品供貨從 14 步手動到一句話的倍數
最有槓桿的下一步 把 agent 接進既有工作流的入口（code review、需求單填寫），這是原訂範圍中唯一未做的兩項
對外的最後一哩 外部串接的邊界已設計完整但無真實流量驗證過，建議先找低風險單位做 pilot
已自認的技術債 網路白名單尚未納入基礎設施即程式碼、審計紀錄含查詢內容需訂存取控制與保留期
關於這份盤點

資料全部來自團隊知識庫的 git 歷史與內部工單系統，經程式化統計後產出，非估算。 統計截止 2026-08-11。

兩點必要的說明：工單以關鍵字撈取，可能漏掉標題未含相關字詞但實質相關的項目， 因此 51 張是下限；且有大量工作直接 commit 未逐項開票， 所以工單數不能單獨當工作量指標。內部主機名稱、帳號命名規則、工單編號、 成員姓名與尚未上線的產品規劃均已移除。
